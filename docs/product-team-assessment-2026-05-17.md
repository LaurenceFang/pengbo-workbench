# Pengbo Workbench 产品团队评估与改进报告

日期：2026-05-17  
评估口径：基于本地下载的多份项目评估报告、当前仓库 README、任务板、公开上传边界文档和安全架构文档。DeepSeek 分享页在当前访问环境没有返回可读正文，因此本报告主要依据本地导出的报告文本与本机仓库事实。

## 一句话结论

Pengbo Workbench 值得继续做，但下一阶段不应该继续把目标扩大成“完整 Bloomberg/Fincept 替代品”。真正能站住的方向是：把它做成一个本地优先、隐私优先、可审计的个人金融研究工作台，让用户从“看一个标的”到“形成一份带来源、缓存状态、风险边界和可导出证据的研究结论”能够稳定闭环。

换句话说，当前最重要的不是多加 20 个功能，而是让产品变成陌生用户也能安装、理解、复现、信任、愿意继续使用的东西。

## 我从这些报告里看到了什么

这些报告的共同判断基本一致：项目方向是对的，架构选择也不是乱拼。Tauri + React + FastAPI + SQLite/DuckDB 适合本地桌面金融工具，README 和安全文档也已经把本地 sidecar、只读数据源、Binance 执行边界、Stronghold、公开上传边界这些关键风险说清楚了。

但报告也同时指出几个硬伤：仓库公开信号弱、缺 LICENSE、没有公开 CI、没有 Release、社区和贡献者几乎为空、Windows 假设很强、数据连接器规模不足、AI 能力不足、专业分析深度不足。这些判断里，有些已经被本地任务板的后续工作部分改善，例如 T48-T52 已经完成了数据源凭证修复、产品手册、安全审计、启动优化和公开上传准备；但 LICENSE、CI、正式 Release、贡献者入口、跨平台构建和外部用户可复现体验，仍然是公开产品信任链的缺口。

几份报告还有一个倾向：容易把“Fincept 有 100+ 连接器、37 个 AI Agent、16 家券商”直接翻译成 Pengbo 的下一步目标。我不同意这种优先级。那是成熟项目的广度结果，不是早期产品的正确起点。Pengbo 如果现在复制广度，会把维护成本、数据合规、测试矩阵和 UI 复杂度一次性拉爆。

## 当前真实状态判断

从本机仓库看，Pengbo 已经不是只有 README 的空壳。它已经有十个工作区、完整的 packaged smoke 脚本、安全架构文档、公开上传边界、任务板验收记录，以及本地打包验证习惯。这个基础比很多开源金融工具更认真。

但从“真正产品”角度看，它还卡在从内部工程项目到外部可信产品的转换期。当前 `package.json` 仍然是 `private: true`，没有 LICENSE 文件，也没有 `.github` workflow。脚本体系以 `py`、PowerShell、Windows target triple 和 packaged EXE smoke 为主，这非常适合当前 Windows-first 桌面验证，但不适合直接宣称跨平台成熟。

所以我会把成熟度定义为：

| 维度 | 当前判断 | 真实产品含义 |
|---|---|---|
| 产品方向 | 清晰 | 本地优先研究工作台是可成立定位 |
| 功能宽度 | 已经偏宽 | 需要收敛到可反复演示的主流程 |
| 工程纪律 | 内部较强 | 外部 CI、Release、版本治理还缺 |
| 安全意识 | 明显强 | T53-T56 前不应做公网或多账户模式 |
| 数据能力 | 有骨架 | 需要能力矩阵、质量分层、无密钥演示 |
| 商业/社区 | 早期 | LICENSE、贡献指南、路线图、首个 Release 是门槛 |

## 产品定位应该怎么改

不要继续主打“穷人版 Bloomberg”。这个说法有传播性，但会把用户预期带到错误地方：用户会拿你和 Bloomberg 的数据、新闻、聊天网络、交易生态、机构采购体系比较，这几乎必输。

更好的定位是：

> Pengbo Workbench 是一个本地优先的个人金融研究终端，把行情、数据来源、研究简报、筛选、因子、回测、纸面交易、工作流和安全边界放进一个可审计的桌面工作台。

面向的第一批用户不要太散：

| 用户 | 他们真正要什么 | Pengbo 应该承诺什么 |
|---|---|---|
| 独立投资者 | 低成本、能看懂、能留痕 | 本地研究闭环和数据来源透明 |
| 个人 PM / 小型资管 | 可复盘、可导出、可控风险 | 报告、审计、只读/交易边界 |
| 量化学习者 | 因子、回测、数据实验 | 可解释模板和本地实验环境 |
| 中文用户 | A 股/港股/宏观数据、中文体验 | 本土数据源、中文默认、低门槛 |
| 教育场景 | 安全、可离线、可教学 | demo 数据、课程化工作流、无实盘风险 |

暂时不应该承诺：机构级 Bloomberg 替代、实时全市场交易终端、多券商实盘执行平台、多用户 SaaS、新闻通讯网络。

## 团队视角评审

### 产品经理视角

现在最大问题不是“功能少”，而是“用户第一眼不知道哪条链路最有价值”。工作区很多，但外部用户会问：我打开它以后，第一件值得做的事是什么？

下一阶段的产品北极星应该是一个可演示闭环：

1. 选择一个标的或主题。
2. 看清数据源状态、凭证要求、缓存/新鲜度。
3. 生成一份研究简报。
4. 关联筛选、因子或回测证据。
5. 导出一份带来源和风险边界的报告。

只要这个闭环稳定，Pengbo 就从“功能集合”变成“工作台”。

### 工程负责人视角

工程上要先补外部可信度：LICENSE、CI、首个 Release、版本号统一、可复现构建、`.env.example`、demo 数据、最小一键启动。当前 smoke 很多是优势，但它们大多是作者本机可执行的证据，外部用户看不到持续集成背书。

第二个工程问题是模块体量和边界。报告里提到 `src/lib/api.ts`、`backend/app/models.py`、`src-tauri/src/lib.rs` 等文件偏大，这类文件会拖慢后续协作。下一阶段应按“变更频率 + 风险边界”拆分，而不是为了抽象而抽象。

### 设计负责人视角

金融终端不需要像营销页。它需要高密度、可扫描、键盘友好、状态明确。Pengbo 已经走过“太丑了”的第一轮 UI 修复，但下一步应该从“好看”进入“专业效率”。

建议做三个交互重点：

1. Command Center：支持 `AAPL research`、`BTC risk`、`FRED CPI` 这类输入式导航。
2. 新手/专业双密度：新手看到解释，专业用户看到更多表格、状态、快捷操作。
3. 数据状态可视化：每个图表、报告、研究结论都应显示来源、新鲜度、是否缓存、是否缺凭证。

### 数据负责人视角

数据源不能只追数量。真正产品化的数据源需要四件事：能力、凭证、缓存、质量。

每个 provider 都应该暴露同一套能力矩阵：

| 字段 | 含义 |
|---|---|
| coverage | 覆盖资产/地区/频率 |
| capabilities | quote/history/fundamentals/news/macro/crypto/trading |
| credential | none/optional/required |
| freshness | realtime/delayed/daily/static/unknown |
| cache_policy | TTL、fallback、离线可用性 |
| quality_status | ok/stale/degraded/unavailable |
| provenance | 数据来源和最后更新时间 |
| trading_boundary | read_only/live_possible/disabled |

先把已有 FRED、CoinGecko、World Bank、DBnomics、RSS、EDGAR、Binance、market provider 做清楚，比盲目扩到 30 个数据源更有产品价值。

### 量化/研究负责人视角

Factor Lab、Strategy Lab 和 paper trading 是潜在亮点，但必须避免把研究信号写成收益承诺。报告、UI 和导出内容里应该继续使用 observed、simulated、blocked、audited 这类证据语言。

下一步应做“研究质量”而不是“策略炫技”：

1. 每个因子给出直白解释、适用资产、样本范围和局限。
2. 每次回测显示假设、手续费、滑点、样本窗口、失败条件。
3. 纸面交易和 Binance intent 保持清晰隔离。
4. 报告里默认加入风险提示和数据来源。

### 安全/合规负责人视角

安全是 Pengbo 的一个真实优势。它已经把本地 sidecar、Stronghold、敏感值、只读 provider、Binance 风控、kill switch、public exposure defer 都写清楚了。

但下一阶段不能因为已有安全文档就放松。T53-T56 的顺序很合理：先本地解锁和 idle lock，再账户化凭证模型，再公共 auth/session，最后才考虑公网/网关/sidecar hardening。任何“团队协作、云同步、远程访问、移动端同步、企业版”都应该被这些任务挡住。

### QA/发布负责人视角

Pengbo 的 packaged smoke 文化是对的，尤其用户已经明确过“软件不是网页”。真正桌面产品必须验证 EXE、installer、AppData、sidecar、Stronghold、UIAutomation，而不是只跑 Vite。

但对外发布需要另一层证据：

1. GitHub Actions 跑基础 CI。
2. Windows Release 构建产生安装包。
3. Release 页面说明校验结果、已知问题和安全边界。
4. 首次启动能无密钥进入 demo 模式。
5. smoke 结果不要直接提交日志文件，而是在 Release notes 中摘要。

### 商业/社区负责人视角

现在商业化不要着急。先解决“别人能不能合法用、能不能装、能不能贡献、能不能信任”。

建议优先选择一条清晰路线：

| 路线 | 许可证倾向 | 适合目标 |
|---|---|---|
| 开源传播优先 | MIT 或 Apache-2.0 | 快速获得用户、贡献者、二开 |
| 商业授权优先 | AGPL + Commercial | 防止闭源商用，但提高采用门槛 |

如果当前目标是先积累用户和反馈，我更倾向 Apache-2.0。商业化可以放在高级连接器、专业模板、企业审计、私有部署支持和培训服务，而不是一开始就靠许可证卡住用户。

## 我建议的下一阶段路线

### P0：产品可信度与首个公开 Release

时间：1-2 周  
目标：让陌生用户能合法、可复现、低风险地试用。

交付：

1. 添加 LICENSE，并在 README 明确许可和商业使用边界。
2. 添加 `.github/workflows/ci.yml`，先跑 `npm run typecheck`、`npm run build`、后端单测。
3. 统一版本号，决定当前是 `0.1.0` 还是 `0.3.0`。
4. 增加 `.env.example` 和 demo 数据模式。
5. 做首个 GitHub Release，上传 Windows 安装包或明确“source preview only”。
6. README 增加真实截图/GIF，展示 1 条完整研究闭环。

验收标准：

1. 新机器按 README 能启动。
2. 无密钥也能进入 demo 数据体验。
3. Release notes 能说明安全边界、已知限制、验证命令。
4. CI 对每次提交给出最小质量背书。

### P1：第一条真正有用的研究闭环

时间：2-4 周  
目标：把“十个工作区”收敛为一条用户能感知价值的主路径。

建议主路径：

Dashboard → Asset → Data Sources → Research → Report Export

交付：

1. 统一数据源能力矩阵。
2. 每个资产页显示数据来源、新鲜度、缓存、凭证状态。
3. Research 简报明确引用数据来源和生成时间。
4. 报告导出包含数据 provenance、假设、风险边界。
5. Command Center 能快速打开标的、研究、数据源和导出。

暂缓：

1. 不急着做 37 个 AI Agent。
2. 不急着做可视化节点编辑器。
3. 不扩大实盘交易范围。
4. 不做多用户、云端、移动同步。

### P2：本地 AI 研究助手，但只作为研究加速器

时间：4-8 周  
目标：让 AI 缩短研究报告生成时间，而不是变成交易决策黑箱。

边界：

1. 默认本地 Ollama/本地模型。
2. 云端模型必须显式授权。
3. AI 只读，不允许直接触发交易提交。
4. 输出必须引用本地数据、报告片段或明确“不足以判断”。

最小形态：

1. Research 页右侧 AI assistant。
2. 输入：当前资产、数据源状态、研究模块结果、用户笔记。
3. 输出：摘要、风险点、待核验问题、报告草稿。

### P3：连接器生态与中国市场差异化

时间：2-3 个月  
目标：从“内置几个源”走向“可维护的数据接入平台”。

建议先做：

1. provider manifest。
2. auth schema。
3. cache policy。
4. connector test contract。
5. A 股/港股/中国宏观的数据源探索。

这里要谨慎。A 股和港股数据源的授权、稳定性、限流和合规比接一个免费 API 更复杂，不能只做能跑一次的 demo。

## 不建议现在做的事

1. 不建议马上把 Workflow Studio 改成自由节点编辑器。当前模板驱动更适合安全边界和可验证性。
2. 不建议马上扩展多券商实盘交易。安全、权限、审计、合规和回放都没准备好。
3. 不建议为了对标 Fincept 盲目堆 30-100 个 connector。先把已有数据源的状态、质量和失败路径做清楚。
4. 不建议把产品讲成“Bloomberg 替代品”。这会带来错误预期。
5. 不建议现在做公网部署或团队 SaaS。T53-T56 没完成前，这条路风险太高。

## 最值得马上放进任务板的新方向

如果要从报告转成执行任务，我建议新增或选择一条“公开可信产品化”路线：

**Public Release And Product Trust Lane**

任务可以拆成：

1. Release Governance：LICENSE、版本号、CONTRIBUTING、SECURITY、issue templates。
2. CI Baseline：前端、后端、最小 smoke 的 GitHub Actions。
3. Demo Mode：无密钥演示数据和第一条研究闭环。
4. Data Quality Matrix：数据源能力、凭证、缓存、新鲜度、provenance。
5. First Release Package：Windows installer、Release notes、截图/GIF、已知限制。
6. Product Onboarding：首次启动向导、示例任务、Manual 到上下文帮助。

这条路线完成后，再去做 AI、插件、节点工作流和更多数据源，成功率会明显更高。

## 最终判断

Pengbo 的机会不是“更便宜的 Bloomberg”，也不是“复制 Fincept 的功能清单”。真正机会是做一个用户能自己掌控数据、密钥、研究过程和风险边界的本地金融研究终端。

当前项目已经有很好的工程骨架和安全意识，但还缺外部产品信任链。产品团队现在应该停止扩大叙事，先把一个可安装、可演示、可复现、可解释、可审计的 v0.1/v0.2 做扎实。

如果我是产品负责人，我会把下一阶段目标写成一句话：

> 让一个从未见过 Pengbo 的用户，在 15 分钟内完成安装，打开 demo 数据，研究一个标的，看到数据来源和风险边界，导出一份可信报告，并知道哪些功能需要真实 API key 才能增强。

做到这个，Pengbo 才真正从“工程项目”变成“产品”。
